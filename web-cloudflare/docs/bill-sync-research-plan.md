# 消费记录自动采集、对账与分类：调研及实施建议

调研日期：2026-10-02。最新进度：已实现 CSV／加密 ZIP 的只读历史核对与本机报告工具，使用虚构数据验证；未接入真实支付账号、邮箱、订单或通知，未写入历史账目。实际能力与限制见 [接入进度](history-import-progress.md)。下文的后台收件、月付原始适配与增量写入仍为计划。

## 1. 目标与事实边界

最新目标：尽量自动收集与批量处理历史消费，近期由用户手动记账，按月核对补漏，在手机 MoneyTalk 查看可靠的消费记录。优先减少历史整理时找邮件、下载、解压、逐笔分类的操作，不以实时通知采集作为本轮目标。成功标准同时考察来源覆盖、账目准确度和用户实际操作次数，不能仅验收一个“上传 CSV”按钮。

本次已完成：检查 MoneyTalk 导入相关代码；检索各平台官方资料和项目维护者文档；只读查询候选 GitHub 仓库的许可、更新时间及发布；审阅部分解析、邮件下载、扩展权限和导出代码。公开代码副本仅用于研究，未运行。

本次未完成：真实手机／账号验证、各 App 当前菜单验证、账单格式兼容性测试、候选工具完整漏洞与依赖审计、免费云端性能测量。项目说明里的“支持”只是候选能力，不等于在用户设备上已可用。

用户已确认：使用苹果手机、系统为其所说的最新版本；白条、美团月付、抖音月付都使用较多，储值卡较少；接受定期汇总；历史尽量自动收集／处理，近期手动录入。未核实具体 iOS 版本，也无需为本轮历史导入额外确认。持续推进要求已写入根目录 AGENTS.md，不为普通实现和测试反复确认。

合理默认：人民币、上海时区；先用最近一个完整月验证，随后整理最近 12 个完整月，再按可取得范围向前补历史。12 个月是试行范围，不是用户确认的上限或平台已验证的导出能力。指定历史截止日期，近期手录照常；补漏文件与手录重叠时先匹配，不能重记。白条及实际使用的月付属于首批核对必需来源；储值卡按实际缺口补充，不开展完整资产／负债管理。

## 2. 调研结论

未找到已经验证、对普通个人账号开放、覆盖全部所列平台的统一全自动接口。搜索到的支付宝和微信账单 API 主要面向商户对账，不能据此宣称能读取个人所有消费。

建议按优先级组合三条输入链路：

1. 官方原始账单：历史消费的主要依据，支付宝、微信与白条／月付需要并行核查覆盖；邮件到达后的步骤尽量自动执行。
2. 购物订单／电子小票：补充商品、店铺、消费日期与分类，特别用于对上信用消费；避免把同一支付再次计入支出。
3. 近期手动记录：保留当前手机记账方式，定期与账单匹配补漏，尊重用户分类和备注。

自动化限制集中在数据离开各 App 之前：申请导出、身份验证、支付密码、解压码、网页登录或验证码。这些操作没有得到真实验证前，不能承诺完全消除。账单申请中的支付密码和银行安全验证由用户完成，不交给浏览器代理；日常采集不需要支付账号密码。

通知／截图自动化改为后续可选研究，不安装手机采集工具、不要求闲置 Android、不把实时通知作为历史数据来源。苹果已公开通知和截图触发器文档，但用户设备行为尚未验证，现阶段不需要依赖它。[苹果事件触发器](https://support.apple.com/en-tm/guide/shortcuts/apd932ff833f/ios)

| 京东 | 支付流水＋京东支付交易流水；网页订单补充 | 区分微信／支付宝／京东支付／白条；订单工具可输出 CSV／JSONL | 找到小型 MIT 扩展和京东支付解析器；扩展不是常驻定时同步器，退款及当前页面仍需验证 |

| 抖音 | 微信／支付宝等支付流水优先；抖音支付／月付另查 | 商品信息和平台支付缺口分别处理；不把抖店商家 SDK 当买家账单接口 | 本轮未核实个人消费完整导出与稳定自动采集入口；商户支付 SDK 不适用此结论 |
| 山姆 | 支付流水记录消费总额；订单／电子小票细化 | 普通支付可先覆盖总额；储值卡、礼品卡、会员费和退款单独处理；混合购物不一律归餐饮 | 本轮未核实个人订单批量接口／自动导出工具；先以账单商户和小票样本验证实际覆盖 |
| 银行／信用卡（按实际使用补充） | 原始账单及自动电子邮件 | 只补支付平台未覆盖的交易；还款、充值、提现不重复当消费 | 已找到多个银行解析器，但不自动扩大为资产管理或读取银行账号 |

支付宝、微信初次采集验证按维护者教程走：支付宝“我的→账单→更多→开具交易流水证明→个人对账”；微信“服务／支付→钱包→账单→客服／常见问题→下载账单→个人对账”。菜单与时间跨度以当前 App 为准，不假设导出能永久自动订阅。先使用 CSV／XLSX，避免把法律证明 PDF 当同一种数据。

依据：[支付宝手机账单教程](https://docs.qianjiapp.com/other/import_guide_alipay_app.html)、[微信教程](https://docs.qianjiapp.com/other/import_guide_weixin.html)、[china_bean_importers](https://github.com/jiegec/china_bean_importers)、[微信商户账单指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071218)、[支付宝商家账单公告](https://developer.alibaba.com/support/announcementDetail.htm?id=25422&source=search)。未找到官方个人 API 是本轮检索结果，不是对未来产品能力的断言。

若做浏览器／Worker ZIP 支持，优先评估 [zip.js](https://github.com/gildas-lormeau/zip.js/)（BSD-3-Clause，2026-09-30 仍有推送），复用加密 ZIP 能力；正式采用前锁定版本、扫描漏洞、量测最终体积和 CPU，不自行实现加密或 CSV 解析器。

## 5. 用户实际要做什么

### 首次：同一份清单，一次准备一个完整月

先统一要收集的日期范围与来源：支付宝、微信、京东订单／白条、实际使用的月付；其他购物平台按付款缺口补充。由助手整理一份按平台分组的简短步骤，用户只完成无法代办的登录、官方申请、支付安全验证及批次解压码。支付和信用账单页面的安全操作由用户在自己的 App 或浏览器完成，不交给浏览器代理。普通购物订单导出工具需在后续核实权限和兼容性后使用。

采集完成后，目标是由程序处理文件识别、下载、解压、格式转换、重复匹配、退款关联与分类。优先验证专用收件邮箱／批量保存到一个文件夹，必要时一次选择多个文件；不要求用户逐笔抄写、每份改名或自行转 CSV。暂不要求常驻电脑、通知设置、新域名或付费服务。自动获取不可行的来源明确退为一次导出后自动处理，不称为完全无人操作。

### 扩大历史：批量处理，先核对再写入

一个月试验通过后按来源可得的日期分批向前整理，先完成默认 12 个月，再补更早可得数据。收件／下载应遍历本次范围内所有批次，不能只拿最新邮件。预览按来源、月份展示记录数、消费额、退款、利息费用、重复与缺口；仅异常需逐项处理。首次真实历史账目写入前确认具体预览，保留原件和批次可撤销能力。

解压码不是支付密码。优先在用户手机／本机解密，或用户按批次提供解压码；不假设解压码固定、不搜集身份证、不猜码。首轮测量实际点击数和时间，再决定是否值得引入常驻采集器。

### 近期与定期：手录照常，每月一次核对

近期沿用手机网页手录。用户在聊天中提供消费，也可先整理成标准记录；当前尚无已验证的聊天自动入账通道，不能宣称已经能直接持久保存。默认每月核对一次：原始账单补漏、更新退款，匹配已有手录，展示真正需要处理的例外。历史和近期以明确截止日期衔接，不因重新导入覆盖手改内容。若本机处理，Mac 只需在整理批次时运行；电脑关机不影响 Cloudflare 手机账本。淘宝／京东工具用于分类补充，其他平台根据实际缺口推进。

## 6. Cloudflare 及执行位置

账本、鉴权、分类规则、同步批次、待确认队列、统计继续用 Cloudflare Worker＋D1。采集端只提交标准化数据，不直接操作 D1。

| 路线 | 用户负担／条件 | 取舍 |
| --- | --- | --- |
| 本机批量文件处理→登录后导入候选账本 | 历史整理时运行；一次提供同批原件和必要解压码 | 当前优先，避免为一次历史整理先搭常驻服务；真实写入需核对预览，不影响云端网页独立可用 |
| 自有域名账单邮箱→Cloudflare Email Worker | 需要可配置 Cloudflare DNS 的域名；平台申请发送到该邮箱 | 收到邮件后的云端流程可自动；workers.dev 免费网址不是自有收件邮箱 |
| 专用 Gmail／QQ 邮箱→采集器→Worker | 需邮箱权限；Gmail API 或 QQ IMAP 等单独核对 | 可不买域名。现成邮件工具仅 QQ；Gmail OAuth 的只读权限仍可能覆盖整个邮箱，不能把代码按标签过滤说成权限只限该标签 |
| 本机按批次邮件采集器→Worker | 历史整理或月度核对时运行，钥匙串保存必要凭据；睡眠后续传 | 免费云端性能不足时的候选方案，不要求全天运行，不能包装成全云端能力 |

Cloudflare Email Routing 需要配置域名／DNS，可把收到的邮件交给 Worker；当前文档列入站邮件上限 25 MiB，免费 Worker 邮件处理仍受 CPU／内存限制。只收件的免费能力不意味着所有解密、XLSX 解析和任意外发邮件都免费。[收件配置](https://developers.cloudflare.com/email-service/get-started/route-emails/)、[价格](https://developers.cloudflare.com/email-service/platform/pricing/)、[限制](https://developers.cloudflare.com/email-service/platform/limits/)

免费 Workers 当前 CPU 额度较小，不能直接把 Python 桌面工具、长时间浏览器、OCR 或大文件解析搬进去。试验先量测典型文件；超额时按数据分批、在手机／浏览器解密或使用已有采集器，必要时讨论付费或外部服务，不自动升级。[Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)

无自有域名时，Gmail API＋定时拉取可作为候选，但需评估 OAuth 类型、权限和持续授权，不把短期测试授权当永久无人值守。QQ IMAP 是否放在本机或其他执行环境由试验决定，不宣称 Cloudflare 原生提供 IMAP 连接器。[Gmail 权限](https://developers.google.com/workspace/gmail/api/auth/scopes)

首批历史导入优先沿用用户登录后的权限，提交候选并核对，不为一次导入先增加永久设备密钥。若后续确需后台收件上传，不能依赖今天的浏览器 Cloudflare Access Cookie：再建立只向指定账本提交候选的受限采集权限，可撤销、有期限、限流；不暴露完整账本、删改权限或 Cloudflare 管理令牌。此处只定义方案，未创建新权限。

## 7. 分类、重复记录和退款：产品规则

### 同一笔消费只计一次

支付宝支付淘宝订单 100 元，淘宝订单、支付宝账单、银行卡扣款和付款通知是四份证据，不是四笔消费。

先保存来源记录，再关联到同一消费。来源内去重以拥有者＋来源账户＋平台＋交易号／事件种类为主；订单号始终用字符串，防止 Excel 科学计数法破坏。跨来源优先支付交易号、商家订单号或明确关系；只有同金额／近似时间／相似商户时进入疑似重复队列，不自动删除，支持合单、拆单、分次付款。

订单只有商品金额、未支付／取消状态时不得生成正式支出。微信和支付宝接入不能覆盖现金、储值卡消费及所有平台自有支付，覆盖缺口明确展示，不能凭导入条数估算全量覆盖率。

### 自动分类的优先级

用户明确修正并记住的规则→商品明细→可信平台原始分类→商户／关键词→待分类。分类是 MoneyTalk 内的稳定 ID，改名不会改变颜色；原始分类保留用于核查。AI 仅辅助不明确的商品描述，不负责猜金额、制造交易、决定是否付款或强行合并账目；默认不把真实消费描述送外部模型。

“美团”可能是外卖、买菜、酒店或打车；“山姆”混合篮子可能包含食品、衣物、家电。没有商品明细时只能分类到合理较粗类别，不伪造细分。若拆分商品，所有分类金额必须严格加总等于已验证实付金额；优惠、运费和尾差规则可解释。

### 退款与非消费

保留原始支付和每次退款，关联原交易；部分退款、跨月退款与取消订单分别处理。充值、提现、本人账户转账、信用卡／白条／月付本金还款不是第二次消费，手续费／利息单独记录；赠礼、红包、转账给他人根据用途分类或待确认，不能一律丢弃。

默认主统计采用消费口径：在成功支付形成消费的日期计商品／服务支出，赊购和分期不等到本金还款日再次计支出。退款按退款发生日单独减支，展示“消费额、退款额、净支出”；这不是银行卡实际出入现金或账户余额。饼图按非负的消费组成绘制，退款另列，明确图表总额对应消费额。真正工资等收入与退款分开；是否需要银行现金流或“原消费月追溯”视图后续评估。

储值充值先作为中性资金移动，消费时才计支出；若没有后续消费明细，报告未覆盖金额，不静默当已完成记账。白条等在消费发生时记商品支出，还本金中性，利息按实际发生记费用。首版不因此增加完整资产／债务管理。

例：1 月用白条买 1,200 元商品，随后 12 期各还本金 100 元。1 月商品消费是 1,200 元，后续本金还款不新增消费；若某期实际收取 5 元费用，单列该期费用。费用以实际账单为准，不按网上通用费率估算，不把未来未发生的利息先记完。[京东分期费用说明](https://help.jd.com/user/issue/201-565.html)

白条退款可能冲抵尚未偿还的分期，已支付服务费也可能不退。因此不能仅看银行卡是否到账判断有没有退款，需对照原订单、退款明细和信用账单。[京东退款与恢复额度说明](https://ihelp.jd.com/n/help/tip/getTipsFacade.json?tipId=80) 月付按用户对应平台实际账单核实，不直接照搬白条规则。

历史边界：导入期内还款对应的购买可能在更早年份。明确标为“历史债务还款／原消费未覆盖”，能取得原订单时向前补证据；不凭还款金额虚构购买日期／分类，不宣称该期间已完整覆盖。订单已包含费用时不可再加一次；本金、费用无法拆清的账单进入待核对。分期合并还款、提前还款、补贴、跨平台退款都需要保留关系。

## 8. 对现有 MoneyTalk 的必要变化

可复用：身份与账本归属、整数分和上海日期校验、提交标识防重复、版本冲突、软删除／回收站、统计、备份校验和批次处理经验。

当前 entries 只有正金额的 expense／income，没有来源交易号、商家订单号、导入批次、退款关系、分类依据或中性事件。现有 restores 是恢复到独立候选账本，不是向当前账本持续增量同步。不能把每次平台同步直接塞进恢复接口，也不能把退款默认变为普通收入。

计划添加来源账户、采集批次、来源交易、证据关联、分类规则和待确认状态；正式账目新增来源关联及退款语义。字段和迁移在样本试验后定稿。备份格式需版本演进，同时支持读取旧 v1；原始文件不得放进现有 200 字备注凑合保存。

新增用户入口优先是“导入与核对”：历史范围、各来源已覆盖期间、手录衔接日期、失败／待输入码、待确认数、自动分类数，以及批次撤销。不能只显示最近抓取时间冒充消费覆盖到今天。正常记录不要求逐条确认，第一次新来源／新模板先预览；后台同步中心在确有需求后扩展。

自动同步尊重用户编辑和删除：重新导入不覆盖手改分类／备注，不复活已删账目；重复文件、重复邮件、同笔多通知只增加证据。批次撤销只影响该批实际新增的正式账目，对之后被用户修改的记录提示冲突，不破坏原有手工账本。

## 9. 阶段与可验收出口

按结果推进，不预设八个平台同时开工。以下工时仅为后续排期单位参考，格式、系统和账号差异可能影响；本轮不承诺固定交付日期。

| 阶段 | 可操作交付 | 用户动作 | 验收出口 |
| --- | --- | --- | --- |
| A：一个完整月的可行性试验 | 支付宝、微信、白条及实际月付的可得格式／脱敏样本；导出步骤计数；候选工具离线对比 | 按统一范围完成必要申请和安全验证；不先整理完整年度 | 每类主要付款方式都确认取得方法；明确缺口、自动／手动边界和真实操作次数，选最省操作路线 |
| B：可靠批量处理与预览 | 来源识别、去重、退款／信用消费关联、分类，生成独立候选账本 | 核对一份按来源和月份汇总的预览；仅处理不确定项 | 消费、还款本金、实际费用、退款分清；金额逐分一致；重叠文件不重记；缺失原消费明确列出 |
| C：获取流程减操作 | 对已验证来源增加指定收件／批量下载、缺码与过期处理；淘宝／京东补分类 | 必要登录、账单申请或解压码按批次提交 | 多封邮件不漏；不默认读取整箱邮件；用户无需逐份解压改名；订单＋支付记录只算一次 |
| D：扩大历史并安全入账 | 默认最近 12 个完整月，逐批向前扩展；真实写入、备份和批次撤销；手录衔接 | 首次真实批次确认具体预览，后续只处理异常 | 每来源覆盖范围有证据；费用退款正确；不覆盖手录；撤销不破坏后续修改；不可得历史保留缺口 |
| E：近期手录与月度核对 | 月度账单补漏、更新退款、保留手改分类；只呈现新增与异常 | 平时手录，每月必要申请／解压码与少量例外 | 连续两个周期核对无未说明差额；手录与导入不重复；记录实际操作次数，云端账本不依赖 Mac 开机 |

不把手机通知自动化、全天采集器、额外设备或付费邮箱作为上述阶段的前置条件。只有来源身份、金额、日期和去重可靠的规则才可按约定写入；未知商户可待分类，不能虚构付款。首轮真实写入核对具体候选批次；当前已实现只读文件核对，尚未执行真实历史入账，详见 [实际进展](history-import-progress.md)。

## 10. 对抗性验收与隐私

| 方向 | 必须尝试破坏的场景 | 通过标准 |
| --- | --- | --- |
| 金额／文件 | GBK、UTF-8 BOM、带逗号金额、长订单号、空值、公式单元格、列顺序改变 | 不浮点误差、不默默跳行；失败行可定位；零元权益不是付费支出 |
| 去重 | 同笔两次通知、同文件重复、重叠月份、两笔同日同额、订单合拆、跨账户 | 强标识唯一；弱匹配不删真记录；重试不重复 |
| 日期／退款 | 午夜、月末、跨月部分退款、退款先到、已退款订单、还款／充值 | 原始事实保留、日期不偏移、未找到原交易进入待核对，不能伪造收入 |
| 白条／月付 | 合并多单还款、本金＋费用、提前还款、退款冲抵欠款、已付费用不退、原消费在导入期前 | 消费只计一次，费用按真实发生，退款不依赖银行卡到账，缺失原消费明确列出 |
| 历史衔接 | 截止日跨午夜、历史文件与近期手录重叠、手录同日同额两笔、补入更早订单 | 明确日期范围；弱匹配不删除手录，不猜历史日期，不重复消费 |
| 同步 | 上传响应丢失、Mac 睡眠、多封账单邮件、邮件链接到期、批次中途失败 | 有本地／云端进度与重试；明确缺口，不用“成功”掩盖漏采 |
| 分类 | 改名、手改后重导、混合篮子、陌生商户、单据写入提示词 | 稳定分类与颜色；手改优先；商品文本不能控制程序、权限或模型工具 |
| 权限 | 伪造来源邮箱、盗用设备令牌、向他人账本上传、撤销后重放 | 固定账本归属、设备可撤销、限流、防重放；采集令牌没有读整本／删除权限 |
| 下载／附件 | 非官方链接、跳转到内网、巨大 ZIP／解压炸弹、路径穿越、损坏加密包 | 限制域名、大小、行数、文件类型和路径；未知链接不抓取，原件不执行 |
| 恢复 | 同步后手工修改、批次撤销、删除后再同步、旧备份 v1 | 不覆盖用户修改、不复活删除、不丢来源证据；旧备份仍可读 |

默认不读取个人整箱邮件，不导出购物 Cookie 到服务器，不上传支付密码、身份证、地址、手机号；专用邮箱／单独采集设备隔离范围。Gmail 的邮箱级权限需如实展示，不以筛选代码虚构最小权限。原始账单含敏感信息，不入 Git，不发第三方 AI；保留位置、加密方式和期限在接入前明示，初始建议本机保留原件、云端仅留必要交易字段与摘要。需要云端短存文件时再评估私有存储与删除规则，不默认创建公开对象存储。

## 11. 已确认与尚待补充

已确认：iPhone、用户表示系统最新；白条、美团月付、抖音月付均较多；储值卡较少；允许定期汇总；历史自动收集／处理优先，近期手录。无需重复询问手机型号、月付平台、闲置 Android 或是否追求当天同步。

实际接入时再一起明确历史日期范围、来源账户、收件／本机文件方式和批次解压码；先按一个完整月试验、12 个月扩展、每月核对推进准备，不为尚未需要的域名或实时采集增加选择负担。能独立完成的样本设计、解析与异常测试持续执行；只有真实样本或本人安全验证阻塞时列出最少操作，不重复问是否继续。

在这些答案之前，默认不索取账号密码、不接入私人邮箱、不安装插件、不部署采集器。可以继续完善脱敏样本测试设计和最小接口计划。后续实际连接需要明确来源范围与数据目的，既有测试账目授权不扩展为读取全部历史真实消费。

## 12. 三大原则落地

面向产品经理：每阶段交付能操作的流程，并报告用户实际动作、同步覆盖期间、已验证与未验证，不用“接了接口”代替可用。

第一性原理：先证明消费金额覆盖与不重记，再用订单细化分类；来源多不代表账目更多。设备只是获取数据的手段，Cloudflare 手机账本仍独立可用。

对抗性思维：资金事实优先于分类猜测，尤其防止白条／月付消费与还款重复；漏采可见、错误可撤销、权限可收回。两次完整核对周期才能证明定期补漏可用，不能以一次演示成功宣布全自动。
