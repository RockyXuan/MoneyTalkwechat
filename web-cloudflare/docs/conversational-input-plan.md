# 口述记账与个人分类规则 · 2026-10-10

## 当前用户目标与范围

主要使用方式是用户看着手机或电脑的消费 App，连续口述多笔消费，由理解层拆分、计算实付金额和分类，再到网站核对并确认。用户可能用 Typeless 等工具先转成文字；当前由本聊天线程承接理解，不要求用户逐笔输入金额、选择分类或填写大段备注。

现阶段复用现有文字批次、草稿、分类、服务器预览及确认接口；不改网站主输入布局，不提前接入语音识别或外部模型服务，不恢复已封存的平台采集。确认尚未稳定之前保持“线程解析 → 网站待确认 → 用户确认后正式入账”。

长段输入目标包含 5、10、20 分钟口述。现有网页只支持一次 10,000 字、40 个候选项目、最多展开 120 笔，不能宣称已覆盖任意长度口述。先由线程分批处理，保留批次来源、消息日期、项目顺序与已处理范围；未来接入栏位时再验证分段、续传、纠正前文和跨段去重。

## 理解与分类约定

- 用户明确指定的分类、用途和人群优先于商品关键词；分类名称按用户意图保留，不静默并入系统默认分类。
- 区分实付、原价、折扣、邮费与合计。明确要求商品和邮费合记时生成一笔；原价或汇总不另记消费。不能把同一句里的每个数字都转成账目。
- 保留商品、平台、可追溯的原文；金额用整数分核对逐笔及分类合计。相对日期以**用户消息发送日、上海时区**为锚点，跨天执行不能改成执行当天的“昨天”。
- 杂谈、计划购买、否定、口误更正、重复描述、退款及还款单独判断；信息不明确的项目保持待确认。不得用缺省零金额、当前日期或固定分类掩盖未知信息。
- 保存草稿与确认入账是两个动作，明确反馈条数、实付合计、日期与是否已计入收支。本聊天生成候选不等同网站已保存；服务器预览不等同已确认入账。

## 个人规则如何积累

先由模型理解新叙述，把用户实际确认的分类、更正和金额处理方式作为规则依据；可确定的固定模式逐步改为可复用脚本，遇到例外仍回到理解与确认。积累半个月或一年并不代表程序自动学会，也不默认训练模型。

规则至少保留适用条件、用户确认来源、例外、版本与回归用例；用户明确指定分类始终高于旧规则。只推广确认过的规律，不将一次商品归类泛化到所有同类词。未确认草稿不能作为已验证学习样本。

实际购物原文、金额、健康消费、个人映射与账本备份只放在拥有者受保护账本或 Git 外私有文件；源码、公开文档和测试只使用虚构案例。未来接入外部模型前再确定数据发送范围、密钥保存方式与费用，不因为线程使用了模型就认为网站已经具备同样能力。

## 分阶段执行与验收

|阶段|交付|可验收标准|
|---|---|---|
|当前：线程理解|逐笔候选、实付与分类合计；复用网站草稿供核对|原文能对应每笔，日期锚点明确，正式账目未提前增加|
|确认后积累规则|保存用户确认与更正，提取高频且明确的映射|正例、反例、例外及冲突优先级可检查，规则不覆盖明确新指令|
|验证长段与分段|虚构长文本，分段来源和去重、更正处理|20 分钟等效文字在限制内分批，无遗漏、无凭空新增、合计准确，失败可续接|
|后续再接网页输入|将已稳定的理解及规则放入主要输入流程，保留手动备用|主入口适合口述文字，集成测试和两引擎 E2E 全通过，线上读回与真实手机验收分开记录|

新增规则或网页能力上线前遵守 `pnpm verify:release` 门禁。重点用虚构例子覆盖原价/实付/合计/邮费、分类标题继承、话题切换、单词误导、重复描述、否定与改口、跨天相对日期、跨段遗漏、失败重试和草稿未确认不入账。当前未实现通用长段模型解析、自动学习或后台自动入账。

## 分类别称的一次点击建议（2026-10-11）

新增私有分类别称与候选 `category_hint`：已明确提供的别称只生成建议，已有同名有效分类优先；确认卡片平铺推荐分类与新建选项，点一次完成本项分类选择，绿色确认仍是正式入账动作。一次选择不会自动训练模型或新增永久别称。别称可在分类管理更正、删除，并随版本 4 备份恢复。通用交互继续遵守“可直接展示就展示，尽量减少点击”，具体实现与验证见 [分类建议方案](category-suggestions-plan-20261011.md)。
